# 广告数据轻量复核与第 39 类接入设计

日期：2026-09-21

## 1. 背景

`data/ad/advertisement_dataset_final.json` 是一个包含 58,658 条记录的 JSON 数组，其中 unsafe 48,652 条、safe 10,006 条。数据已经完成初始分类和清洗，本次任务只做轻量质量复核，暂不与现有最终数据集合并。

当前广告数据包含 4 个广告大类和 16 个 `attack_scenario` 小类。最终标签体系需要新增单一第 39 类广告风险，并继续使用现有小类作为 `attack_scenario`。

只读结构检查已经确认：

- 所有记录都有非空且唯一的 `trace_id`。
- 所有记录的 `scene` 都是 `prompt`，且 `prompt` 非空。
- `label` 只包含 `safe` 和 `unsafe`。
- 当前数据中 `label` 与 `extended_info.is_attack` 没有结构性冲突。
- unsafe 记录均有广告大类和 `attack_scenario`，safe 记录没有错误携带风险字段。
- `annotation.method` 均为 `auto`，`quality_score` 均在 `0..1` 范围内。

上述检查只能证明结构一致，不能证明语义标签正确。

## 2. 目标

本次复核解决三个问题，优先级从高到低如下：

1. 复核原始 `safe` / `unsafe` 是否正确。
2. 识别样本是否同时明确命中现有 38 类风险。
3. 弱检查原 `attack_scenario` 是否存在明显错误，但不自动改写小类。

输出只分为确认无问题的数据和需要人工查看的数据。确认无问题的记录保持原有字段和值不变。

## 3. 非目标

- 本阶段不与 `data/final` 下的现有数据合并。
- 不自动修改原始数据。
- 不自动决定重叠样本最终使用第 39 类还是原 38 类。
- 不自动修正 `attack_scenario`。
- 不要求模型生成新解释、风险等级或质量分。
- 不使用 Safety Review 多角色流水线完成这次轻量复核。

## 4. 标识与顺序

### 4.1 `trace_id`

所有持久化状态、问题清单、分流结果和后续合并都必须直接使用原始数据中的 `trace_id`。

- 不生成新的 `trace_id`。
- 不替换原 `trace_id`。
- 不给原 `trace_id` 添加前缀或后缀。
- 不使用内容哈希代替原 `trace_id`。

批内可以使用从 0 开始的短整数 `i` 压缩模型输入输出，但该整数只在单次请求中有效。本地代码必须通过请求快照把 `i` 确定性映射回原 `trace_id`，不得依赖模型返回或生成 `trace_id`。

### 4.2 输入顺序

分流结果分别保留各自在原始输入中的相对顺序。最终校验必须证明正常池和问题池的 `trace_id` 无交集，二者并集与原始输入完全一致。

## 5. 第 39 类广告风险

### 5.1 正式枚举

第 39 类的正式英文枚举为：

```text
advertisement
```

在后续获准生成修正版时：

- 确认属于广告风险的 unsafe 样本使用 `extended_info.risk_type=advertisement`。
- safe 样本不填写 `risk_type`。
- 当前 16 个小类继续原样保存在 `extended_info.attack_scenario`。

### 5.2 当前 4 个广告大类

当前数据中的下列值不再作为最终风险大类：

- `external_site_advertisement`
- `spam_advertisement`
- `contact_advertisement`
- `in_game_trading_advertisement`

本次复核不修改这些字段。后续生成修正版时，由确定性本地代码把它们统一归一化为 `advertisement`。如果确有审计需要，可在独立清单中保留原值，不应由模型重新生成。

## 6. 与原 38 类重叠的处理

最终 8-4 格式的 `risk_type` 是单值字段，因此本次不引入多标签结构。

判定原则如下：

- 内容主要是普通营销、联系方式引流、外部网站引流、垃圾广告或游戏交易广告时，广告风险是主类。
- 广告只是表达载体，而内容本身明确命中原 38 类中的实质风险时，记录为 `legacy_overlap`。
- `legacy_overlap` 只表示候选主风险需要人工确认，不在本阶段自动修改 `risk_type`。
- 人工确认后如果选择原 38 类作为主风险，广告小类仍可保留在 `attack_scenario`，以免丢失广告场景信息。
- 模糊、证据不足或无法确定主风险的样本进入问题池，不得默认视为正常。

## 7. 模型审查协议

### 7.1 模型输入

每个批次只向模型发送完成语义判断所必需的信息：

```json
{"items":[{"i":0,"p":"待复核提示词","s":"wechat_contact"}]}
```

字段含义：

- `i`：批内短序号。
- `p`：原始 `prompt`。
- `s`：原始 `attack_scenario`；safe 样本为空字符串。

模型输入不包含：

- 原始 `trace_id`；本地代码持有映射。
- 原始 `label`，避免确认偏差。
- 原始 `risk_type` 和 4 个广告大类。
- 原始 `explanation`、`source`、`quality_score`。
- `response`；所有记录的正式审查场景均为 `prompt`。

### 7.2 模型输出

模型只返回紧凑结构，不返回解释或原文：

```json
{"r":[{"i":0,"l":1,"x":"","s":0}]}
```

字段约束：

- `i`：必须对应输入中唯一的批内序号。
- `l`：模型独立判断的标签，`0=uncertain`、`1=safe`、`2=unsafe`。
- `x`：明确命中的原 38 类风险枚举；没有明确重叠时为空字符串。
- `s`：原 `attack_scenario` 是否明显错误，`0=未发现明显错误`、`1=明显可疑`。

本地校验必须拒绝以下结果：

- 结果数量与输入数量不一致。
- `i` 缺失、重复或越界。
- `l` 或 `s` 不在闭集中。
- `x` 不是空字符串且不属于原 38 类闭集。
- `l=safe` 但同时返回非空 `x`。

模型格式错误、结果缺失、请求失败或达到最大重试次数的记录均进入问题池，不得进入正常池。

## 8. 本地分流规则

本地代码按原 `trace_id` 把模型结果与原记录比较，并生成一个或多个问题代码：

| 条件 | 问题代码 |
| --- | --- |
| 模型返回 `uncertain` | `uncertain` |
| 模型标签与原 `label` 不一致 | `label_error` |
| `x` 非空 | `legacy_overlap` |
| `s=1` | `scenario_suspect` |
| 请求或校验最终失败 | `provider_failure` 或 `invalid_result` |

只有同时满足下列条件的记录才能进入正常池：

- 模型给出确定标签。
- 模型标签与原标签一致。
- 没有明确的原 38 类重叠。
- 原 `attack_scenario` 未被判为明显可疑。
- 请求和结构校验全部成功。

问题可以同时存在。例如一条记录可以同时具有 `label_error` 和 `scenario_suspect`。

## 9. 批处理与恢复

复用现有批量任务的以下能力：

- SQLite 持久化和断点恢复。
- 并发、RPM、TPM 和共享冷却。
- 请求重试与失败分类。
- 批量响应缺项检测。
- 上下文过大时递归拆分批次。
- 安全进度日志，不输出原始数据内容。

批次不能只按固定条数切分。调度器应在保留系统提示词和最大输出空间后，按保守 Token 估算贪心装入尽量多的连续记录。配置同时保留最大条数作为安全上限。供应商报告上下文过大时，对批次二分重试；单条仍过大时进入问题池。

模型最大输出 Token 应随批内记录数设置合理上限，避免为紧凑结果预留过量输出空间。

## 10. 模型选择

不能只根据模型名称断言某个 Flash 模型已经达到 safe/unsafe 复核质量要求。采用逐级验证：

1. 首先用 `qwen3.5-flash` 运行分层试样。
2. 试样覆盖 safe、全部 16 个广告小类、不同文本长度、低质量分记录和疑似原 38 类重叠记录。
3. 人工检查所有模型建议改标签的记录，并随机检查模型确认正常的记录。
4. 如果 `qwen3.5-flash` 未达到要求，再用相同试样评估 `deepseek-v4-flash`。
5. 全量任务只使用通过试样的最轻模型。Pro 模型只作为后续可选的争议样本复核手段，不作为默认全量模型。

模型配置使用阿里云 OpenAI 兼容地址：

```text
https://aigateway.venusgroup.com.cn/ai/aliyun/openai
```

API Key 只从配置的环境变量读取，不写入配置、日志或产物。

## 11. 输出产物

本阶段生成以下独立产物，不触碰原始文件：

### 11.1 `clean.original.jsonl`

保存确认无问题的原记录。除从 JSON 数组转为 JSONL 表示外，所有字段和值保持不变，不追加模型结果或审计字段。

### 11.2 `issues.original.jsonl`

保存至少有一个问题代码的原记录。记录本身保持不变，方便人工直接查看。

### 11.3 `issues.manifest.jsonl`

只保存必要审计信息：

```json
{"trace_id":"原始 ID","issues":["legacy_overlap"],"candidate_legacy_risk":"other_illegal_or_prohibited_content"}
```

不得包含 `prompt`、`response`、完整模型响应或凭据。

### 11.4 汇总报告

报告只包含聚合计数、枚举分布和必要的 `trace_id` 列表，不复制原始文本。至少统计：

- 正常池和问题池数量。
- `label_error` 的 safe→unsafe 与 unsafe→safe 数量。
- `legacy_overlap` 按原 38 类候选的分布。
- `scenario_suspect` 按原小类的分布。
- `uncertain`、请求失败和格式失败数量。
- 各批次输入、输出 Token 和平均装载条数。

## 12. 验证与验收

### 12.1 确定性校验

- 原始输入、正常池和问题池均可完整解析。
- 输入总数等于正常池数量加问题池数量。
- 两个输出池内部均无重复 `trace_id`。
- 两个输出池的 `trace_id` 无交集。
- 两个输出池的 `trace_id` 并集与输入完全一致。
- 每个输出记录的 `trace_id` 与原记录完全相同。
- 对每个输出记录做规范化 JSON 值比较，除数组转 JSONL 的表示差异外，内容与原记录完全相同。
- `issues.manifest.jsonl` 中每个 `trace_id` 都存在于问题池，且每个问题池记录都有清单项。

### 12.2 语义抽检

- 人工检查全部 `label_error`。
- 人工检查全部 `legacy_overlap` 或按数量分批检查。
- 对正常池做按原标签、场景和文本长度分层的随机抽检，以评估漏报。
- 对 rare `attack_scenario` 保证最小抽检覆盖，不让大类分布掩盖小类错误。

### 12.3 后续阶段

只有用户确认问题池的处理规则和修正结果后，才能生成修正版广告数据。修正版通过完整结构、闭集、去重和分布检查后，才进入与既有最终数据集的合并设计。
